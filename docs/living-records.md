# 거주 중 기록 저장

마이페이지의 **거주 중 기록 보기** 또는 메인 화면의 **거주 중 문제 대처**에서 사진·상황을 저장하고 다시 조회할 수 있습니다. 사진·상황 저장과 유형별 대처 안내는 별도 동작입니다. 대처 안내는 AI 판독 결과가 아닙니다.

## 준비

- 기존 Supabase 프로젝트에 001~005가 적용되어 있는지 먼저 확인합니다.
- `supabase/migrations/202611140006_living_records.sql`을 한 번 적용합니다. 기존 입실·퇴실 사진 테이블은 수정하지 않습니다.
- `backend/.env`와 `frontend/.env`의 실제 연결값을 설정합니다. `.venv/bin/python scripts/check_setup.py`는 값 노출 없이 형식을 확인합니다.
- Render에서는 `main`을 선택하고 `render.yaml`에 맞춰 API(`backend/`)와 정적 프론트(`frontend/`)를 배포합니다. 프론트의 `VITE_API_BASE_URL`은 배포된 API 주소, 백엔드의 `CORS_ORIGINS`는 프론트 주소로 설정합니다.
- Supabase Auth의 허용 리디렉션 주소에도 프론트 주소를 등록합니다.

## API와 보관

- `POST /api/living-records`: Bearer 인증, multipart `file`, `category` (`mold`, `wall`, `other`), `description` (1~2000자), `upload_id` (UUID).
- `GET /api/living-records`: 로그인한 사용자의 주택에 속한 기록만 반환합니다. 주택 미등록 시 빈 목록이며, 저장하려면 주택 등록이 필요합니다.
- 사진은 기존 비공개 `deposit-private` 버킷에, 메타데이터는 `living_records`에 보관합니다. 사진은 최대 20MiB이며 실제 이미지 형식과 해상도를 검사합니다.
- 읽기는 사용자 JWT와 RLS로 제한하고, 파일 쓰기는 서버가 주택 소유권을 확인한 뒤 수행합니다. 임시 사진 주소는 15분 후 만료되며 **다시 조회**로 갱신합니다.
- 재시도 시 같은 `upload_id`를 사용합니다. DB 응답이 유실되면 저장 여부를 조회하여 중복 저장 및 저장된 사진의 잘못된 삭제를 방지합니다.
- 로그아웃 시 화면과 미리보기를 해제합니다. 기기 로컬 저장소에 기록을 저장하지 않습니다.
- 현재 기록 삭제·수정 기능은 제공하지 않습니다.

## 검증 범위

자동 테스트는 모의 Supabase HTTP로 업로드·재시도·조회·권한 검사를 수행하고, PGlite에서 실제 SQL과 RLS를 검증합니다. 프론트 테스트는 실패 후 재시도·재마운트 조회·HTML 이스케이프를 확인합니다.

실제 Supabase 프로젝트의 SQL 적용, 로그인 후 업로드·재로그인 조회, 실제 모바일 브라우저 및 배포 환경 연결은 별도 검증이 필요합니다. 로컬 설정이 예시값인 동안 실제 저장 또는 배포 완료로 간주하지 않습니다.
